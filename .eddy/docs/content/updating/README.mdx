# Update your extension

When Eddy changes, you can merge the changes into your extension: new CI jobs, tooling releases, fixes to the build and the docs it generates. Your own code and your own changes to the template stay as they are. This page shows how to update with Claude Code or by hand, and what stays current between updates.

:::info Coming from 4.x?

An extension created from a 4.x release needs a one-off upgrade to 5.x first: its `AGENTS.md` fetches the update skill from a URL that returns 404, and the upgrade replaces `.devtools/` with the tooling package and CircleCI with GitHub Actions. [Upgrade a 4.x project to 5.x](upgrading-from-4x.mdx) walks you through it.

:::

## Update with Claude Code

If you use Claude Code, ask Claude to "update scaffold" in your project. The `AGENTS.md` that Eddy generated tells Claude to fetch the [`update-consumer-eddy`](https://github.com/drevops/eddy/blob/main/.eddy/skills/update-consumer-eddy/SKILL.md) skill with these commands, and then to follow it:

```bash
mkdir -p .claude/skills/update-consumer-eddy
```

```bash
curl -fsSL -o .claude/skills/update-consumer-eddy/SKILL.md \
  https://raw.githubusercontent.com/drevops/eddy/main/.eddy/skills/update-consumer-eddy/SKILL.md
```

The skill renders 2 releases, the release your project is on and the latest one, with answers it reads from your project as it is now. Then it merges the difference between them into your project:

```mermaid
flowchart LR
  base["The release your<br/>project is on"] --> diff["Difference<br/>between releases"]
  latest["The latest<br/>release"] --> diff
  diff --> merge["3-way merge<br/>into your project"]
  project["Your project"] --> merge
  merge --> pr["Pull request"]
```

Only lines that both sides changed need a decision. The skill then builds, lints and tests the result, and opens a pull request. Without a command wrapper, it leaves the lint and the tests to the pull request's CI.

Your extension's own code stays out of the merge, and so do your own files and your changes to the template. The skill changes these files on top of the merge:

- It takes `scripts/eddy-tooling` from the release, and lists any change you made to it in the pull request.
- It removes a template file that the release removed, even when you changed it, and lists it in the pull request.
- It keeps your `package-lock.json`, and regenerates it when the merged `package.json` changed.
- It finds references in the docs and configurations to example files that your project doesn't have, and points them at your own files or removes them.
- For a project from 4.x, it removes `.devtools/`, `.circleci/` and the Cloudflare tunnel hooks.

The skill decides these from what it finds:

- **Which release.** Without a tag, the skill updates to the release with the highest version among the 10 most recently published releases that aren't drafts or marked as pre-releases on GitHub. To update to a particular release, name its tag: `/update-consumer-eddy <tag>`. When your project is already on that release or a newer one, the skill stops, unless you add or drop a Drupal major.
- **Which release you're on.** The skill reads it from `extra.eddy.version` in `composer.dev.json`, which an installer from a GitHub archive and every update record, or from your last scaffold update commit. An extension created from a branch download records the commit it came from, such as `5.0.0-3-g1a2b3c4`, and the skill renders that commit in place of a release. Without a recorded release, or with one older than 4.14.0, every difference between your files and the new release's comes up for a decision.
- **Adding or dropping a Drupal major.** Ask for it in the same request, such as `/update-consumer-eddy add Drupal 12`. The skill changes the major's CI jobs and badges, and for a new major, makes the code changes it needs, each in a commit of its own. It does this even when there's no newer release to update to.
- **Permissions.** On its first run, the skill might add a few command permissions to `.claude/settings.local.json` and ask you to restart Claude Code. Run it again after the restart.

## Update by hand

To update without Claude Code:

1. [Run the installer](../installation.mdx#run-the-installer) in a new, empty directory, and repeat the answers your project uses. That directory isn't a clone of your repository, so pass the branches your workflows run on and your GitHub repository, such as `INSTALL_BRANCHES=1.x,2.x INSTALL_GITHUB_REPOSITORY=owner/myextension php install.php`. To update to a release other than the latest, or to the current code, [install from a download](../installation.mdx#install-from-a-download) instead.
2. Create a new branch in your extension's repository.
3. Copy the new files into your extension's directory, apart from your extension's own code: `src`, `tests`, `config`, `css`, `js`, `composer.json`, `logo.png`, the files named after your machine name and `scripts/*-example.sh`. The new files hold the example extension under your machine name, so copying those would overwrite your code.
4. Resolve the differences between the new files and yours. Keep your own branches in the workflow branch filters and your repository in the README badges, unless you passed them in step 1. Keep `scripts/eddy-tooling` exactly as the release ships it.
5. Check the release notes for breaking changes.
6. [Build the site](../development/building.mdx), [check coding standards](../development/coding-standards.mdx) and [run the tests](../testing/README.mdx).
7. Commit and push to your GitHub repository, and check that every CI job passes.
8. Merge the new branch into your main branch, and check that the deployment job works.

## What else stays current

Between scaffold updates, these parts stay current on their own:

- The [tooling package](../development/tooling.mdx) takes its patch releases within the `~` constraint in `composer.dev.json`. CI installs the newest on every run, and a local checkout takes it after `reset`. A scaffold update raises the constraint for a new minor version.
- When you keep Renovate, it keeps the npm packages, GitHub Actions and Docker images up to date (see [Dependency updates](renovate.mdx)).
