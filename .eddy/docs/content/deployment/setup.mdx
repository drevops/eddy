# Set up deployment

CI pushes to your extension's Drupal.org repository with an SSH key. This page walks you through creating the key and the repository secrets that turn [deployment](README.mdx) on. Use a dedicated key for each project, so you can revoke 1 without touching the others.

## Before you start

Make sure you have the following:

- Admin access to your extension's GitHub repository, to add secrets and variables.
- Push access to your extension's repository on Drupal.org.
- `ssh-keygen`, which comes with OpenSSH.

## Add the SSH key and the secrets

1. Generate a new SSH key without a passphrase:

   ```bash
   ssh-keygen -m PEM -t rsa -b 4096 -C "your_email+project_name@example.com"
   ```

   `ssh-keygen` asks where to save the key. The private key goes to that file, and the public key to the same name with `.pub` added.

2. Add the **public** key to your [Drupal.org account](https://git.drupalcode.org/-/user_settings/ssh_keys).
3. Add the **private** key as the `DEPLOY_SSH_KEY` secret in your repository's **Settings** → **Secrets and variables** → **Actions**.
4. Add these secrets in the same place:

   - `DEPLOY_REMOTE` - your extension's Drupal.org repository, such as `git@git.drupal.org:project/myextension.git`. Until it's set, the deployment job reports a notice and skips deployment.
   - `DEPLOY_USER_NAME` - the name that git uses on the CI runner, such as your name on Drupal.org. The deployment fails without it, although the deployed commits keep their own authors.
   - `DEPLOY_USER_EMAIL` - the email address that git uses on the runner, such as your email address on Drupal.org. It's required, like `DEPLOY_USER_NAME`.
   - `DEPLOY_PROCEED` - set to `1` after CI works and you're ready to deploy. Without it, the deployment job runs but doesn't push, which lets you test the job.

5. Optional: Set `DEPLOY_BRANCH` to the branch to push to in the destination repository. It isn't a secret: add it as a repository variable under **Settings** → **Secrets and variables** → **Actions** → **Variables**. Without it, the code goes to the branch that triggered the build. Tags are always pushed as tags.

The **Actions** secrets of your repository then list `DEPLOY_SSH_KEY`, `DEPLOY_REMOTE`, `DEPLOY_USER_NAME`, `DEPLOY_USER_EMAIL` and, when you've set it, `DEPLOY_PROCEED`.

## Confirm that it works

Before you set `DEPLOY_PROCEED`, push a commit to a branch that deploys, such as `1.x`, and watch the `Deploy` workflow that starts after `Test` passes. The job ends with "Skip deployment because DEPLOY_PROCEED is not set to 1." Set `DEPLOY_PROCEED` to `1`, and the next push reaches your Drupal.org repository.

:::tip Other destinations

Nothing about the job is specific to Drupal.org: `DEPLOY_REMOTE` can name any git remote that accepts the key, such as a mirror on another git host.

:::
