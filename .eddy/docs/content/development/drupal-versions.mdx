# Drupal versions

`DRUPAL_VERSION` sets the Drupal version to build. Leave it unset and the build uses your project's default, which is `11`, the newest stable Drupal 11 release, unless you chose otherwise in the installer. This page shows how to build another version, and how the build picks the version of core and of every other dependency.

## Build another version

Set `DRUPAL_VERSION` before the build:

<CommandTabs
  make={`# Newest stable Drupal 11 release.
DRUPAL_VERSION=11 make build

# Newest Drupal 11.1.x patch release.
DRUPAL_VERSION=11.1.0 make build

# Newest Drupal 11 beta, release candidate or stable release.
DRUPAL_VERSION=11@beta make build

# Newest stable Drupal 12 release, or newest pre-release if none.
DRUPAL_VERSION=12 make build`}
  ahoy={`# Newest stable Drupal 11 release.
DRUPAL_VERSION=11 ahoy build

# Newest Drupal 11.1.x patch release.
DRUPAL_VERSION=11.1.0 ahoy build

# Newest Drupal 11 beta, release candidate or stable release.
DRUPAL_VERSION=11@beta ahoy build

# Newest stable Drupal 12 release, or newest pre-release if none.
DRUPAL_VERSION=12 ahoy build`}
  none={`# Newest stable Drupal 11 release.
DRUPAL_VERSION=11 vendor/bin/eddy-assemble

# Newest Drupal 11.1.x patch release.
DRUPAL_VERSION=11.1.0 vendor/bin/eddy-assemble

# Newest Drupal 11 beta, release candidate or stable release.
DRUPAL_VERSION=11@beta vendor/bin/eddy-assemble

# Newest stable Drupal 12 release, or newest pre-release if none.
DRUPAL_VERSION=12 vendor/bin/eddy-assemble

# After any of them, start the server and install the site.
vendor/bin/eddy-start
vendor/bin/eddy-provision`}
/>

To keep a version for every build, add a line such as `DRUPAL_VERSION=11.1.0` to your project's `.env` file instead. A non-empty value in your shell wins over the one in `.env`.

After you change the version, [build the site](building.mdx) again. `assemble` rebuilds the codebase from scratch every time, so you don't need to run `reset` first.

The value names a release line rather than an exact release, and the build picks the newest release on it. The major is always fixed, and so is every number before the last one. So `11.1.0` and `11.1.5` both build the newest 11.1.x release, while `11` and `11.1` both build the newest 11.x release. The build can't pin an exact patch release.

A pre-release is an alpha, a beta or a release candidate. A stability flag of `@stable`, `@rc`, `@beta` or `@alpha` lets pre-releases down to that stability qualify, as in `11@beta`. A development branch isn't a release, so the build rejects `@dev` and stops with "No Drupal release matches".

## The default version

The default comes from `extra.eddy.drupal-version` in `composer.dev.json`:

```json
"extra": {
    "eddy": {
        "drupal-version": "11"
    }
}
```

The installer sets it to the highest Drupal major you selected that has a stable release. Eddy treats 11 as the newest major with one, so selecting 10, 11 and 12 sets `11`. When you selected only majors newer than 11, it sets the lowest of them. When neither `DRUPAL_VERSION` nor `extra.eddy.drupal-version` is set, the build uses Drupal 11.

## How versions are resolved

The build pins Drupal core to the newest release that matches `DRUPAL_VERSION`, and prints the release it picked. When no release on that line is stable enough, such as a major with no stable release, it takes the newest pre-release on the line instead.

Every other dependency gets its most stable release that fits, because the build uses `minimum-stability: dev` with `prefer-stable: true`. A dependency falls back to a pre-release or a development branch only when no stable release fits the rest of the build: core, the other dependencies and the platform PHP. The build output lists every dependency it installed from a development branch. So nothing needs editing as Drupal and its tools publish new releases: the next build picks them up.

### The PHP requirement

Before it touches the `build` directory, the build checks the PHP that runs it against the PHP requirement of the chosen core release, and stops with a message when the release needs a newer PHP. It then sets `config.platform.php` in `build/composer.json` to that PHP, so a `platform` setting in your global Composer configuration doesn't apply.

To resolve for another PHP version on purpose, set `config.platform.php` in `composer.dev.json`, or in your extension's `composer.json`, where `composer.dev.json` wins. The build checks that version against the requirement too.

### What a version resolves to

The following table shows the core release that each kind of value builds:

| `DRUPAL_VERSION` | Drupal core                                                                                                       |
|------------------|-------------------------------------------------------------------------------------------------------------------|
| `11`             | The newest stable 11.x release.                                                                                   |
| `11.1`           | The newest stable 11.x release, the same as `11`.                                                                 |
| `11.1.0`         | The newest stable 11.1.x release.                                                                                 |
| `11@beta`        | The newest 11.x release at beta stability or above: the next minor's beta or release candidate when one exists, otherwise the newest stable release. |
| `11@alpha`       | The same as `11@beta`, with alphas too.                                                                           |
| `12`             | The newest stable 12.x release, or the newest 12.x pre-release while 12.x has no stable release.                  |
| `11@dev`         | None: the build stops with "No Drupal release matches".                                                           |

When no release on a line qualifies, the build takes the newest pre-release on that line, so `12` builds the newest Drupal 12 pre-release until 12.0.0 ships.

Drush resolves like any other dependency, so each build gets the most stable Drush that supports its core.

## Drupal 12

Drupal 12 requires PHP 8.5 or newer, so a local Drupal 12 build needs it too:

<CommandTabs
  make={`DRUPAL_VERSION=12 make build`}
  ahoy={`DRUPAL_VERSION=12 ahoy build`}
  none={`DRUPAL_VERSION=12 vendor/bin/eddy-assemble
vendor/bin/eddy-start
vendor/bin/eddy-provision`}
/>

On an older PHP, the build stops before it changes anything and says which PHP the release needs.

Until Drupal 12 has a stable release, `DRUPAL_VERSION=12` builds its newest pre-release. After 12.0.0 ships, the same value builds the newest stable 12.x release, with no change on your side.

A Drupal 12 build differs from the others in 3 ways:

- It installs PHPUnit 12, which Drupal 12 core requires.
- It installs `drupal/core` from source, because the core packages leave out the test base classes and the PHPUnit bootstrap, so it takes a little longer to assemble.
- It installs Drush from its `14.x` development branch until Drush publishes a 14.x release, pre-releases included.

Drupal 12 is opt-in in the installer, where only Drupal 11 starts checked. Selecting it next to Drupal 11 adds `^12` to `core_version_requirement`, its CI jobs and its README badge. The local build stays on Drupal 11, because the default is the highest selected major with a stable release. [Continuous integration](../continuous-integration/README.mdx#drupal-12) explains how the Drupal 12 jobs follow its releases, and [Upgrade a 4.x project to 5.x](../updating/upgrading-from-4x.mdx#drupal-12) lists the changes your own code needs.
