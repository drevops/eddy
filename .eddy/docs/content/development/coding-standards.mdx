# Coding standards

`lint` checks the codebase with every linter you kept in the installer, and `lint-fix` runs the ones that can fix what they find. Both stop at the first tool that fails. This page lists the tools, where they run and how to fix what they report.

To check and fix the codebase, run the following commands:

<CommandTabs
  make={`make lint       # Check coding standards
make lint-fix   # Fix what the tools can fix`}
  ahoy={`ahoy lint       # Check coding standards
ahoy lint-fix   # Fix what the tools can fix`}
  none={`cd build
vendor/bin/phpcs
vendor/bin/phpstan
vendor/bin/rector --clear-cache --dry-run
vendor/bin/twig-cs-fixer
npm run lint
cd ..
npm install
npm run lint-spell`}
/>

## The tools

`lint` runs the tools in the order of the following table. Their configuration files sit in the root of the codebase, so you tune a rule in the same place for your machine and for CI.

| Tool                                                            | What it checks                                                                                  | Configuration                         | Fixes |
|-----------------------------------------------------------------|-------------------------------------------------------------------------------------------------|---------------------------------------|-------|
| PHPCS                                                           | PHP against the `Drupal`, `DrupalPractice`, `DrevOps` and `PHPCompatibility` standards for PHP 8.3, and `declare(strict_types=1)` in every file. | `phpcs.xml`                           | Yes   |
| [PHPStan](https://phpstan.org/)                                 | PHP with static analysis, with [PHPStan Drupal](https://github.com/mglaman/phpstan-drupal).    | `phpstan.neon`                        | No    |
| [Drupal Rector](https://github.com/palantirnet/drupal-rector)   | PHP for deprecated Drupal code. Rector also applies the PHP 8.3 upgrade sets and strict types, plus its dead code, code quality, coding style, type declaration, privatization and naming sets. | `rector.php`                          | Yes   |
| [Twig CS Fixer](https://github.com/VincentLanglet/Twig-CS-Fixer) | Twig templates.                                                                                | `.twig-cs-fixer.php`                  | Yes   |
| [ESLint](https://eslint.org/)                                   | JavaScript, with [Prettier](https://prettier.io/) formatting.                                   | `.eslintrc.json`, `.eslintignore`, `.prettierrc.json`, `.prettierignore` | Yes   |
| [Stylelint](https://stylelint.io/)                              | CSS.                                                                                            | `.stylelintrc.js`                     | Yes   |
| [CSpell](https://cspell.org/)                                   | Spelling across the codebase.                                                                   | `.cspell.json`                        | No    |

## Where they run

The PHP and JavaScript tools run from the `build` directory, where the assembled site gives them Drupal core and your dependencies, so [build the site](building.mdx) before you lint. ESLint and Stylelint check the extension through its directory in the site, and they only run when the build installed the frontend dependencies (see [Frontend dependencies](dependencies.mdx#frontend-dependencies)).

`assemble` copies the configuration files into `build`, so an edit to one applies after the next `assemble`. Edit the files in your project, not the copies in `build`.

CSpell runs from the project root instead, and reads `.cspell.json` in place. It installs the root `package.json` dependencies first when `node_modules` is missing. It checks every text file that git doesn't ignore, apart from hidden files and directories, such as `.github`, and the paths in the `ignorePaths` of `.cspell.json`.

## Fix what the linters report

`lint-fix` runs Rector, PHPCBF, Twig CS Fixer, ESLint and Stylelint with their fix options. PHPCBF is the fixer that comes with PHPCS. To fix what the tools can fix, run the following command:

<CommandTabs
  make={`make lint-fix`}
  ahoy={`ahoy lint-fix`}
  none={`cd build
vendor/bin/rector --clear-cache
vendor/bin/phpcbf
vendor/bin/twig-cs-fixer --no-cache --fix
npm run lint-fix`}
/>

Review the changes before you commit them. When an automatic fix is wrong, adjust the tool's configuration to suppress the issue or change the fix.

## Spelling

CSpell checks prose, code and inline code in Markdown, and skips fenced code blocks. An unknown word fails the check, so a new term needs a home:

- Add a word the whole project uses to the `words` of `.cspell.json`.
- Add a word only 1 file uses to that file, in a comment such as `cspell:ignore laminas` written in the file's own comment syntax.

## In CI

CI runs the same tools in its `lint` jobs, 1 per Drupal major you test, with CSpell first. To let a tool fail without failing its job while you work through its findings, set its [ignore-failure variable](../continuous-integration/configuration.mdx#allow-a-ci-step-to-fail).
